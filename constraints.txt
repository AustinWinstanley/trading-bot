#
# Combined, reproducible version pins for the three requirements files
# in this repo (requirements.txt, dashboard/requirements.txt,
# mcp_server/requirements.txt) — Dockerfiles install with
# 'pip install -r <requirements-file> -c constraints.txt' so container
# images are reproducible across builds while the requirements files
# themselves keep loose ranges for local development.
#
# Regenerate with:
#   pip install pip-tools
#   cat requirements.txt dashboard/requirements.txt mcp_server/requirements.txt \
#     | pip-compile --upgrade --output-file=constraints.txt -
# (--upgrade picks up new releases within each requirements.txt's own
# range ceilings; omit it for a no-op idempotency check instead.)
# pip-compile emits `pyjwt[crypto]==...` (mcp's own dependency on pyjwt
# carries the [crypto] extra) — a pip constraints file cannot contain
# extras syntax ("Constraints cannot have extras"), only name==version.
# After regenerating, manually strip `[crypto]` from the pyjwt line; mcp's
# requirement still applies the extra at install time, this file only
# needs to pin the version.
#
# Before accepting ANY Dependabot bump to this file (or the ceiling in
# mcp_server/requirements.txt's cryptography<43 line), regenerate fully
# via the command above rather than accepting Dependabot's own partial
# per-package edit — a partial edit only bumps the lines Dependabot's
# dependency graph flagged as "direct", which can silently produce an
# internally-inconsistent lock (e.g. bumping pydantic-core independently
# of pydantic's own pin on it, which pip then refuses to resolve). See
# the 2026-08-14 git history for a real instance of this.
